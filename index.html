Part 1 · before the session, about 15 minutes

Set up your laptop

Do this at home if you can. At the end, one script tells you whether you are ready.

  1. 5 min

    Follow the access instructions from your organizer. Open Bob, open the chat panel and type hello. You should get an answer.

  2. 1 min
    Terminal
    python3 --version

    You need Python 3.9 or higher. No version? Install Python from python.org, then try again.

  3. 1 min
    Terminal
    node --version

    Not installed? Fine. Scenario 4 can target Java, Swift, Go or C# instead.

  4. 1 min

    Clone the repo into a folder with no spaces in its path, for example your home folder. The last word in the command is the name of the folder it creates:

    Terminal
    git clone https://github.com/barissozen95/bobathon.git bobathon

    No Git installed? Download the ZIP, unpack it and rename the folder to bobathon. It contains app/, scenarios/, GUIDE.md and this guide (index.html).

  5. 3 min

    In a team of two or three, share your work through GitHub:

    1. One person forks the repo on GitHub and adds the others under Settings → Collaborators.
    2. Everyone clones that fork: replace the address in the command above with your fork's address.
    3. Everyone works on their own branch, commits the output and pushes it:
    Terminal, inside bobathon
    git switch -c s3-alice
git add scenarios
git commit -m "S3: RouteQL interpreter"
git push -u origin s3-alice

    Scenario output goes to scenarios/<scenario>/out/ and plans/. Don't touch the input files. Fetch a teammate's branch with git fetch, or open a pull request in your fork and review each other's work.

  6. 1 min

    In Bob: File → Open Folder… and choose bobathon itself, not a parent and not app.

    Every @/… path in this guide starts from that folder. Opening the wrong folder is the most common reason Bob "can't find" a file.
  7. 1 min

    Open Bob's terminal (or any terminal) inside bobathon:

    Terminal
    bash setup-check.sh

    On Windows run it in Git Bash or WSL. Without either, run the two commands in Part 3 by hand instead.

    You should see
    Bobathon setup check

  OK    Python 3.9.6 (python3)
  OK    CampusRoute tests: Ran 63 tests in 0.5s
  OK    CLI works (python3 -m campusroute route ...)
  OK    Node v22.x (Scenario 4 default target)
  OK    port 8000 free on 127.0.0.1
  OK    Bob skill + custom mode present (.bob/)

Ready. Open this folder in Bob and start with GUIDE.md.

    Ready = go. Ready with warnings = some scenarios are unavailable, and the WARN lines tell you which. Not ready = show the output to the facilitator.

Scenario 3 · Build

Build a programming language: RouteQL

Kiosk operators want to script routes: route "Main Gate" to "ENG-B204" avoid stairs. Bob plans a lexer, parser and interpreter. You review the plan, Bob implements it against the real routing engine, and 16 acceptance tests decide.

Coding PythonTime ~10 min, tightBob Plan → new task → Agent, approvals, running testsCard scenarios/s3-build-a-language/CARD.md
The interpreter must never use eval, exec, compile, os.system or subprocess. Otherwise a .rql file could run any code on your laptop. One test feeds it __import__("os") on purpose.
  1. 3 min
    Plan mode
    Plan a RouteQL interpreter per @/scenarios/s3-build-a-language/routeql-spec.md. Do not write code yet.
Write the plan to scenarios/s3-build-a-language/plans/routeql-plan.md (one file). Cover: lexer (token kinds), parser (one statement per line, recursive descent from the EBNF), AST classes, interpreter, how it imports campusroute from app/ (sys.path relative to the script), error handling with "Error on line N: ..." on stderr and exit codes 0/1/2, and verification with @/scenarios/s3-build-a-language/test_routeql.py.
Constraints: Python 3.9 standard library only; no eval/exec/compile/os.system/subprocess; output file scenarios/s3-build-a-language/out/routeql.py; no features beyond the spec.

    If Bob asks clarifying questions, click an option.

  2. 2 min

    • Parse first, then run: a syntax error on line 2 must print nothing at all for line 1.
    • Vague words like "handle errors appropriately": ask for the exact message format.
    Plan mode, example change
    Add to the plan: the whole file is parsed before anything runs, so a syntax error produces no stdout at all. Update the plan file.
    Stop here if you must. Producing and critiquing a plan is the core outcome.
  3. 3 min

Do not modify test_routeql.py or anything under app/.

Scenario 4 · Build

Port a real module to another language

The mobile client needs schedule.py on-device with the same behavior. Translating is easy. Translating so 20 tests still pass is engineering.

Coding yesTime ~10 min, tightBob Ask analysis, Agent port, tests, literate codingTarget JavaScript (Node 18+), or Java / Swift / Go
  1. 2 min
    Ask mode
    @/app/campusroute/schedule.py I will port this to JavaScript (Node 18, ES modules, no dependencies). List every place where a naive translation would change behavior. Check specifically: weekday numbering, % with negative numbers, // vs Math.floor/trunc, dict insertion order, csv quoting, str.isdigit, datetime arithmetic, sort stability, None. For each: line number, Python behavior, JS pitfall. Max 10 bullets.
    Open two of the line numbers. Is the code there? Python's weekday() is Monday = 0. What is JavaScript's getDay()?
  2. 3 min
    Agent mode
    Port @/app/campusroute/schedule.py to JavaScript as scenarios/s4-translate-code/out/schedule.mjs (ES module, Node 18+, no dependencies). Preserve behavior exactly, including error messages. Handle the traps from your analysis explicitly and mark each with a comment starting "PY:". Do not modify anything under app/.

    The approval card should write only out/schedule.mjs.

  3. 4 min
    Agent mode, same chat
    Port @/app/tests/test_schedule.py to scenarios/s4-translate-code/out/schedule.test.mjs using node:test and node:assert/strict. Same inputs, same expected values. Every Python test must have a JS counterpart with the same name. Run: node --test scenarios/s4-translate-code/out/
If a test fails, fix schedule.mjs. Never change an expected value to make a test pass.
    If Bob changed a test, compare it line by line with test_schedule.py. A changed expected value is the most common way a "successful" port is actually broken.
    Steps 1 and 2 are the core.
  4. 1 min

    Open out/schedule.mjs, click inside parseDay, press Cmd + I or click the magic wand icon, and type:

    Literate coding instruction
    also accept Turkish day abbreviations Pzt, Sal, Car, Per, Cum, Cmt, Paz

    Press Generate (Cmd + Enter). Read the inline diff. Accept with Cmd + Enter, reject with Cmd + Shift + Backspace. Re-run the tests.

    One test should now fail (bad day uses Pzt). Is the test wrong or the change? Decide, and explain why.
  5. +3 min
    Agent mode
    Temporarily replace the weekday mapping in scenarios/s4-translate-code/out/schedule.mjs with a plain date.getDay(), run node --test scenarios/s4-translate-code/out/, report how many tests fail, then revert the change.

    If zero tests fail, your ported tests are too weak to protect the code.
